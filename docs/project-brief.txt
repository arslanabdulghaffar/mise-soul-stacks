Bimanual table setting with verified recovery
Multi-modal Instruction to Skill ExecutionTeam MISE  |  Online build 10 to 16 September 2026
The revised project
We will build two simulated SO-101 arms that set a dinner table from a natural-language instruction, check whether each manipulation actually worked, and recover from a failed grasp when a valid corrective action remains. A browser dashboard will show the cameras, task plan, recovery decisions, randomized runs and Intel performance measurements.
The primary workflow includes a drawer, plate, mug, spoon and fork, with a real object hand-off between the arms. A small vision-language planner selects registered learned skills. A temporal monitor checks progress, and a constrained supervisor decides when to continue, retry, replan or stop. MuJoCo and inference run locally on the Intel demonstration machine.
Assessment and decision
Keep MISE, but change the execution strategy. The concept matches the challenge well. Its main weakness is delivery risk: the original plan simultaneously commits to reinforcement learning, large-scale simulation, two distillation pipelines, quantization-aware training and several policy backends. Those commitments compete with the work that earns most of the score: a complete task, meaningful reasoning and measured Intel deployment.
The revised plan makes imitation learning and early Intel export the default. We retain recovery as the distinguishing feature, add a visible website, and make advanced training conditional on a working baseline. A stronger proposal alone does not establish a winning probability. The evidence from the completed system will determine whether the submission is competitive.
Submission priorities
• A complete randomized table-setting task with genuine coordination between both arms.
• A measurable recovery benefit over a fair retry baseline, without hidden resets.
• A convincing website that exposes recorded evidence and identifies live versus replay mode.
• A reproducible Intel execution package with supported, measured OpenVINO optimization.

Where the original proposal overclaims
Existing robotics work already studies feedback-driven planning and failure correction. We should credit that prior work and describe MISE as a focused integration for bimanual manipulation on Intel hardware. The potential distinction is the measured combination of valid recovery, bounded action execution and transparent evidence. Claims that no other team will build recovery should be removed. [10, 11]
Judging strategy: show a complete task first, expose one informative failure and recovery second, and then prove the execution and optimization claims. Additional models earn no credit merely by appearing in the architecture.

The official SO-101 notes flag removed base collision meshes and a gripper mapping mismatch. Validate base collision geometry and explicit gripper conversion before scoring collisions or grasps. Pouring is an extension after the core task passes. Tilting a bottle above a mug proves a motion, not liquid transfer. Confirm the required pouring criterion with organizers. If a simplified particle-transfer task is accepted, score transfer and spill explicitly and label the simulation approximation. Until implemented, commands requiring pouring are unsupported and must be reported as such. Parallel reaching and a second policy backend are also optional.
3 Runtime architecture and instruction contracts
We use a vision-language planner with learned ACT motor skills. This is a hierarchical system. The brief permits ACT and related imitation policies, so one end-to-end VLA is not required. [2, p. 2]
Figure 1. Proposed runtime. The website receives execution evidence; the evaluator cannot supply hidden object state to the controller.
Observation and action contracts
At deployment, models receive RGB, robot joints, command fields and action history. Reserve true object poses and contact labels for training and an isolated evaluator. Log the observation schema and prevent evaluator-to-controller leakage. The brief allows simulator state; this stricter boundary makes visual grounding testable.
Start with three 256 by 256 policy cameras: overhead and both wrists. Use the VLM checkpoint's native image processor. Include both arms' joints for single-arm skills, and verify action order, units and gripper conversion against the robot manifest.
Planner and skill binding
Start by testing the documented InternVL2_5-1B family in OpenVINO. Use constrained outputs and a fixed skill vocabulary. Verify scene understanding and export compatibility before committing; defer planner distillation. [5]
Each step records skill, object, goal, arm, preconditions, dependencies and timeout. A registry selects the trained checkpoint and normalization metadata. JSON fields alone do not condition ACT: use task-specific checkpoints first, and add shared conditioning only after training and export verification. [6]
Preserve required arms and sequence words. Skip satisfied goals only when permitted by the instruction. Reject invalid or cyclic plans. After one repair attempt, use a disclosed parser only for the supported grammar; otherwise report an unsupported request.
4 Coordination and valid recovery
Coordination rules
Execute sequentially by default. Shared-zone labels are a scheduling aid, not collision checking. Reserve arms and manipulated objects, hold the inactive arm at a validated pose, and check joint limits, velocity limits and robot geometry using joint-based forward kinematics. Hand-off reserves both arms until receiver retention is confirmed. Keep deliberate gripper contact distinct from forbidden arm or object collisions.
Cancel queued actions whenever a skill changes, recovery starts or a newer observation invalidates the chunk. Attach sequence numbers and timestamps to actions. Replan at stable states; continue any required holding controller while the planner runs. Stop or enter a controlled hold if observations or actions exceed their tested freshness limit.
The monitor and supervisor
Use a small visual encoder with temporal history, joint changes, active skill and action progress. Target 10 Hz monitoring and measure detection plus cancellation delay under load. A single RGB frame cannot establish slip velocity or distinguish every occluded grasp. Train visual predicates such as object-held, object-in-goal and progress-stalled. The supervisor maps these observations to explicit states:

Allow at most two recovery attempts per skill and a 180 s episode budget initially. Validate these limits before the final run. A simulator reset always starts a new episode and never counts as autonomous recovery.
Correcting the original recoverability labels
If every tested continuation fails, the original draft labels the state as retryable. That is not justified. Evaluate actual candidate actions from the same saved state, including regrasp and feasible arm transfer. Prefer student-policy rollouts; teacher-only labels can overestimate what the deployed policy can recover. Report estimated recoverability under the tested candidates, never global proof that a task is impossible.
5 Training and integration strategy
Use the stated training resources to remove observed bottlenecks. More GPUs do not resolve reward design, gripper geometry, camera rendering, dataset errors or Intel export failures. A successful expert trajectory and a working learned export are more useful on the first day than thousands of unstable training environments.
Default training route
• Build scripted IK or teleoperation experts for the declared primitives. Record real contacts, images, joint targets, skill boundaries and outcomes in a pinned LeRobot-compatible format.
• Start with roughly 100 to 300 successful demonstrations per task-specific skill, plus failure and recovery trajectories. These are starting data budgets, not sufficient-data claims. Add data where validation fails.
• Train ACT baselines with identical train and deployment preprocessing. Separate checkpoints by primitive, target and goal when necessary. Train both-arm outputs for the hand-off, including grasp acquisition and release timing.
• Run students in the environment early. Collect correction data at missed grasps, contact transitions and unfamiliar starts. Where the expert is valid, use DAgger-style corrections on student-visited states.
• Export a real checkpoint to OpenVINO before scaling training. Validate action order, output range, normalization and closed-loop behavior against its source model.
Monitor data and calibration
Use simulator predicates offline to label short sequences, then retain only observable inputs for the monitor. Include successful trajectories, delayed motion, empty grasps, recoverable drops, occlusion and terminal failures. Keep all clips and forked continuations from one parent episode in the same data split; adjacent frames are not independent samples.
Start with a progress detector and deterministic, feasible retry rules. Add candidate-conditioned recoverability estimates only after the complete loop works. For each saved failure state, simulate bounded candidate continuations and estimate their success fractions. Freeze monitor thresholds on validation episodes and report false intervention rate, missed failures and time-to-detection.
Advanced training is conditional
Privileged RL teachers, MJX acceleration, planner distillation and quantization-aware training are optional upgrades. Add one only when a measured failure justifies it and integration time remains. MJX has backend-specific contact, feature and rendering constraints, so porting the scene is a separate engineering task. CPU MuJoCo with parallel data-collection processes is the first fallback. [7]
Keep the first deployed policy backend fixed. Replacing ACT with SmolVLA late in the build changes training, preprocessing, export and latency simultaneously. A second backend is useful only if it solves a demonstrated limitation and passes the same evaluation.

Small evaluation set with useful comparisons
Plan 50 nominal episodes including the required 10, 20 held-out episodes, and a separate 20-case recovery suite. On the recovery suite compare: no retries; bounded retry with the same visual verifier; and the proposed monitored recovery. Keep policies, seeds, timeouts and retry budgets fixed. For Intel precision preservation, compare reference and optimized models on the same 50 nominal seeds.
This is approximately 180 episode runs across configurations. At a 180 s timeout and real-time factor 1, simulation alone can take 9 hours. Reserve that time after code freeze and add reset, compilation and recording overhead. If throughput is lower, preserve the required 10 and the most informative paired comparisons first.
Metrics and interpretation
Report full-task success, completed-step fraction, hand-off success, collisions, constraint violations, recovery attempts, recovery success and wall-clock completion time. Give numerators, denominators and 95% Wilson intervals. Even 10 successes out of 10 have a Wilson lower bound of about 72%, so ten runs cannot establish near-perfect generalization.
Test reasoning with the same command in changed scenes and changed commands in the same scene. Measure correct next actions and constraint compliance. Parse validity alone measures formatting. Predeclare at least 20 such cases and retain the camera evidence and accepted plan for each.

Optimization sequence
Establish source-framework reference behavior, then verify an OpenVINO reference model. Try post-training quantization using training/validation contact and recovery states; never calibrate on final test data. Keep sensitive output layers at higher precision if needed. NNCF supports accuracy-controlled quantization, but manipulation quality still requires closed-loop validation. QAT is a fallback when calibration and mixed precision cannot meet the target. [9]
Use a provisional control target of 30 Hz, with ACT re-inference initially every three control steps. This creates a 100 ms refill budget, not a claim of 30 Hz neural inference. Measure end-to-end p95 latency, action age and deadline misses. Asynchronous inference must discard stale chunks and preserve time alignment; interpolation alone does not demonstrate fast inference.
What the benchmark must record
Record hardware SKU, RAM, OS, power mode, runtime and driver versions, model hashes, actual devices and precision. Separate compilation and warm-up from steady-state timing. Report per-model p50/p95 latency, throughput and memory, plus full-loop control rate, real-time factor, observation-to-action age and CPU/iGPU/NPU utilization where measurable.
Use paired task-success results to justify the chosen precision. A provisional engineering target is no more than a 5 percentage-point drop, with raw paired outcomes and uncertainty disclosed. Report unsupported placements explicitly. Keep a slower placement only when full-system measurements show a benefit, and never claim zero quantization loss or free monitoring without evidence.
8 Website visual design
Build one polished MISE Robotics Console. The first screen should explain the task within seconds and make the robot execution the visual focus. Judges should be able to move directly from an observed action to its plan step, recovery event and recorded result.
Figure 2. Website design concept with a schematic scene. The final viewport uses actual MuJoCo camera frames; metrics remain empty until a recorded run supplies them.
Visual direction
Use a graphite background, restrained cyan accents for arm A and violet for arm B, clear white text and subtle panel borders. Keep color assignments consistent in the viewport, timeline and replay. Use large camera views, concise labels, a visible command bar and a compact task panel. Avoid decorative 3D backgrounds that compete with the actual robot.
Proposed design tokens: background #0A101A, panel #142135, primary text #E6EDF5, secondary text #91A7BF, arm A #73D4E4 and arm B #A293EF. Use a locally bundled sans-serif font, 8 px spacing increments, 12 px corner radii and 150 to 200 ms state transitions. Status must have text or icons as well as color.
Desktop layout uses a narrow navigation rail, a large camera area and an adjacent plan panel. Below 900 px, stack the camera and plan and replace the rail with compact navigation. At 390 px, every essential control remains reachable without horizontal scrolling. Keyboard focus, reduced-motion support and readable text are part of the design.

The strongest interactive demonstration
Offer a clearly labeled challenge mode with a few reproducible perturbation presets: a displaced object, a reduced-friction grasp, or a partially completed table. The same preset and seed must be replayable for baseline and recovery configurations. Online physics perturbations, if offered, are validated, bounded and logged as a separate stress test; they do not silently enter the main benchmark.
When recovery triggers, the interface highlights the exact event, displays its evidence and shows the chosen corrective action. Use short status messages such as "Object not retained after lift" and "Regrasp attempt 1 of 2". Display a measured confidence only if it is calibrated. Behavior when the system is unavailable
Show LIVE, RECORDED REPLAY or DISCONNECTED prominently. On disconnection, disable commands and show the last observation timestamp. When replay is selected, expose the original run ID, seed, model version and Intel hardware record. An unknown metric is displayed as unavailable, not zero.
Manual reset, operator intervention and changed instructions create explicit events. A run needing assistance must not count as autonomous success. A paused evaluation run is either excluded from timing with a disclosed reason or reported in a separate assisted category.
What to leave out
Do not spend hackathon time on accounts, payment systems, social feeds, voice control or a second browser physics engine. The useful website is the working robot interface and its evidence. Public visitors can inspect recorded runs without requiring the Intel machine to remain online.
10 Website implementation and data flow
Use a React and TypeScript frontend built with Vite, with utility CSS or a small token stylesheet. Serve the compiled frontend and API from FastAPI on the Intel machine for a single-origin local demo. FastAPI supports WebSockets for live event delivery. Keep simulation in a separate worker process so slow browsers cannot block control. [12]
Data flow
The simulation worker produces timestamped observations and action outcomes. A bounded queue sends telemetry and display frames to the API. The browser receives structured events over WebSocket and camera frames through a separate stream. Start with JPEG/MJPEG at 10 to 15 display frames per second; upgrade transport only if measured latency or bandwidth requires it. Control and inference rates remain independent of display rate.

Presentation narrative
MISE turns a natural-language table-setting request into coordinated actions for two simulated arms. Each skill is checked against an observable outcome. When a grasp fails, the system can attempt a bounded correction or revise the remaining plan while preserving the original instruction. Its dashboard lets the viewer inspect what happened, which action was selected and whether the task ultimately succeeded.
The demonstration runs simulation and inference on Intel Core Ultra hardware. We compare controller variants on the same randomized conditions and measure the precision and device choices we actually deploy. The useful claim is improved completion under those tested conditions, supported by downloadable run evidence.
Questions to be ready to answer
• What does the policy learn, and which parts are deterministic? Show the skill registry and observation schema.
• Does the planner use images? Show paired scene interventions and their plans.
• Is recovery better than simply retrying? Show the matched baseline and the same time budget.
• Is the website actually controlling the robot? Show its live mode, Intel worker and event timestamps.
• Did the optimization preserve behavior? Show paired outcomes and full-system measurements, including failures.
If a result is not yet measured, say so. Do not use invented FPS, perfect success percentages, anonymous benchmark graphs or a selectively edited recovery to fill a presentation gap.
